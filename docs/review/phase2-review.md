## Summary

1. No Critical: double booking cannot occur — every writer of `show_seats` runs check-and-act under
   `FOR UPDATE` in one transaction, with `chk_show_seat_*`, composite FKs and
   `uq_one_live_ticket_per_seat` as backstops (see Verified OK).
2. Worst findings: **confirm ignores show/event status** (a booking can be CONFIRMED on a cancelled
   show — this exact core is slated for the Phase-3 payment webhook), and **idempotent replay breaks
   on uppercase UUIDs** (422 instead of 200).
3. Refresh-token rotation has a race (no row lock) and reuse is not contained (no family revocation);
   expiry of refresh tokens is checked against the JS clock, breaking rule 4 under multi-instance.
4. Robustness: no `statement_timeout`/`lock_timeout`/`connectionTimeoutMillis`, no `pool.on('error')`
   (process crash on DB restart), unvalidated UUID path params return 500, bulk seat insert can
   exceed the 65,535 bind-parameter limit.
5. Lock order (reservation → booking → show_seats, seats ascending) is respected in every core path;
   the only ordering risk involves `cancelEvent`'s `UPDATE shows` — listed under Needs verification.
6. Event/show cancellation is a state-machine hole throughout (can republish a cancelled event;
   HELD seats and PENDING_PAYMENT bookings are never reconciled).

  confirm `src/modules/bookings/bookings.service.ts:182-275` (res `bookings.repository.ts:183-196` → booking `:199-211` → same ordered seat lock).
  `createReservation` holds `FOR SHARE` of the show before reservation/seat locks (`reservations.repository.ts:76-83`), but `FOR SHARE` is mutually compatible and the only conflicting show-row writers (`cancelEvent`) never take reservation/booking/seat locks — no cycle among the four core paths (the residual 3-way case is V-1). `markSeatsBooked`/`holdSeats` update seats without `ORDER BY` only on rows this transaction already locked in order.
- **Takeover cannot hit the new holder** (probe): release filters `WHERE reservation_id = $1 AND status = 'HELD'` (`reservations.repository.ts:227-248`) — a seat re-held by another reservation is untouched; checkout and confirm verify Rule D (`ss.reservation_id === mine && hold_valid`) **before** any write (`bookings.service.ts:146-155`, `:229-244`) and fail with 409 `HOLD_LOST`. Was covered empirically by `test-phase2-step5.js` Test 5 (script removed in Step 6; not yet ported to the Vitest suite).
- **Double booking at the DB level (rules 1, 2)** — check-and-hold happens under `FOR UPDATE` in one transaction (`reservations.service.ts:153-173` + `reservations.repository.ts:146-178`), with DB backstops: `chk_show_seat_hold`, `chk_show_seat_booked` (migration 002 `:78-82`), composite `(reservation_id, show_id)` / `(booking_id, show_id)` FKs (`:75-76`), `UNIQUE (show_id, venue_seat_id)` (`:73`), `bookings.reservation_id UNIQUE` (`:48`), and `uq_one_live_ticket_per_seat` (`:107-108`). `scripts/verify-002.sql` exercises each constraint.
- **DB clock in the booking engine (rule 4)** (exceptions in M-3): hold expiry `now() + make_interval` (`reservations.repository.ts:136-141`); lazy expiry `held_until < now()` in availability (`reservations.repository.ts:155`) and in the seat map (`show-seats.repository.ts:71`); `expires_at > now()` for `is_active_valid` (`bookings.repository.ts:84`, `:189`); `sales_open`/`not_started` computed in SQL (`reservations.repository.ts:77-79`).
- **Tickets only on confirmation (rule 6)** — checkout inserts `bookings` but no `booking_seats` (`bookings.service.ts:157-166`; was asserted by the since-removed `test-phase2-step5.js` Test 1, not yet ported to the Vitest suite); confirm creates `booking_seats` and verifies count + price-sum against the booking (`bookings.service.ts:251-257`) and checks `err.constraint === 'uq_one_live_ticket_per_seat'` (`:269`). **Probe "BOOKED ⇔ exactly one live ticket":** unreachable through current API paths (both writes are atomic in one transaction with count checks); note the converse (`live ticket ⇒ seat BOOKED with same booking_id`) is asserted only by the manual `scripts/check-invariants.sql:6-19`, not by any constraint — see test gaps.
- **Checkout/confirm idempotency (rule 7, happy paths)** — one booking per reservation (`bookings.repository.ts:94-106`, replay under the reservation lock); confirm replays on `status === 'CONFIRMED'` (`bookings.service.ts:204-210`); concurrent double-checkout and 10-way confirm race asserted by `scripts/smoke-checkout.mjs` scenarios A/B. Reservation create replays on `(user_id, idempotency_key)` with payload-equality → 422 on mismatch (`reservations.service.ts:77-97`).
- **`ON CONFLICT DO NOTHING` race is safe (probe)** — `insertReservation` (`reservations.repository.ts:135-143`) targets `(user_id, idempotency_key)` explicitly, which uses PostgreSQL *speculative insertion*; a concurrent same-key inserter is waited out (PostgreSQL "Index Uniqueness Checks" + `execIndexing.c` `CEOUC_LIVELOCK_PREVENTING_WAIT`), so when `RETURNING` is empty the winner has committed and the re-read finds it (`reservations.service.ts:127-149`). `scripts/smoke-concurrency.mjs` scenario 3 asserts 10 parallel identical requests → all 200/201, one reservation id. (Contrast M-1: *sequential* replay of a since-expired reservation is the broken case.)
- **`uq_one_active_reservation` vs stale ACTIVE rows (probe)** — the only insert path first expires the requester's stale rows (`expireStaleActiveReservations`, `reservations.repository.ts:110-122`) and a residual conflict is correctly mapped via `err.code==='23505' && err.constraint==='uq_one_active_reservation'` → 409 `ACTIVE_RESERVATION_EXISTS` (`reservations.service.ts:202-208`). A stale ACTIVE row can block its owner only until their next create attempt, which self-heals (the misreporting read is M-1).
- **Someone else's resource → 404 (rule 8)** — venues (`venues.service.ts:12-17`), events (`events.service.ts:11-14`, `:24-28`, `:38-42`), reservations (`WHERE id=$1 AND user_id=$2`, `reservations.repository.ts:206`, `:220`), checkout (`bookings.service.ts:100-103`), bookings (`:291-294`, `:304-307`). Mock confirm is 404 when disabled (`:286-288`) and `ENABLE_MOCK_PAYMENT=true` is rejected in production (`src/config/env.ts:18-24`).
- **SQL injection (rule 10)** — all queries use `$n` placeholders; dynamic SQL is confined to whitelisted literals: `updateEvent`'s SET columns (`events.repository.ts:41-71`), `updateEventStatus`'s ternary `setClause` (`:74-77`), `insertBulkSeats`/`insertCategoryPrices` placeholder generation (`venues.repository.ts:54-70`, `shows.repository.ts:36-45`). No user input reaches identifier position.
- **Client handling / transactions (rule 9)** — every multi-statement write runs inside one `withTransaction` with the single acquired client (`src/db/pool.ts:16-32`); no `pool.query` occurs inside a transaction (grep-verified: only `src/app.ts:33` health check uses `pool.query`); all `pool.connect()` call sites release in `finally` (`events.controller.ts:72-110`, `shows.controller.ts:24-30`). Postgres error→HTTP mapping happens outside the transaction in both mapped cases (`reservations.service.ts:202-210`, `shows.service.ts:84-113`, `bookings.service.ts:268-274` re-throws).
- **Cookie / token handling basics** — refresh cookie `httpOnly`, `secure` in production, `SameSite=strict`, scoped `path:'/auth'` (`auth.controller.ts:6-12`); only a SHA-256 hash of the refresh token is stored (`auth.service.ts:17-21`, migration 001 `:39-47`); argon2id password hashing and hash never serialized (`auth.service.ts:47`, `src/modules/auth/password.ts`); roles restricted at registration to ATTENDEE/ORGANIZER (`auth.schema.ts:7`) and `requireRole` checked on all organizer routes.
- **Env validation** — Zod-validated env with fail-fast `process.exit(1)` and mock-payment-in-production guard (`src/config/env.ts:6-32`).
- **Multi-instance (probe)** — no in-process state affects correctness: holds, expiry, idempotency and locking are all DB-side; two instances behind an LB behave like one except for the JS-clock items (M-3) and the shared-secret/`ENABLE_MOCK_PAYMENT` env consistency requirement.
- **Request body size** — `express.json()` default 100 kb limit applies (`src/app.ts:15`).

## Test gaps

Scenarios that no existing script (`scripts/smoke-*.mjs`, `test-phase2-step*.js`, `test*.js`, `verify-002.sql`) covers:

1. **Cancellation at every stage** (H-1, M-2): cancel while a hold is ACTIVE / booking PENDING_PAYMENT / booking CONFIRMED; confirm-after-cancel; republish-after-cancel; create-show-on-cancelled-event.
2. **UUID case** (H-2): replay with uppercase `seatIds`; same seat twice in different cases; uppercase ids across checkout/confirm paths.
3. **Idempotent replay of dead reservations** (M-1): replay after natural expiry; after takeover by another user; after `DELETE`; assert the reported `status`/seat ownership.
4. **Refresh-token rotation races** (H-4): two concurrent `POST /auth/refresh` with one cookie (assert exactly one survives); reuse of a revoked token (assert family revocation once implemented).
5. **Concurrent register with the same email** (M-9): assert 201 + 409, never 500.
6. **Bulk seat edge cases** (M-5): duplicate `rows` entries, re-run of the same bulk payload, >13 107 seats (bind-parameter cap), venue seat cap.
7. **Malformed path params** (M-4): `GET /events/abc`, `POST /venues/abc/seats/bulk` etc. — assert 4xx, not 500.
8. **Release/confirm after takeover** (probe): old holder's `DELETE /reservations/:R` and `POST /bookings/:B/confirm-mock` racing the new holder's create — assert the new holder's `show_seats` rows are untouched (only the checkout variant existed, in the since-removed `test-phase2-step5.js` Test 5).
9. **`uq_one_active_reservation`** (probe): second concurrent create for the same user+show with a *different* key while the first is ACTIVE → assert 409 `ACTIVE_RESERVATION_EXISTS` (never tested).
10. **Cross-show / foreign seats**: `seatIds` belonging to another show (assert 400, no partial hold) — only implicitly covered.
11. **Cancel-vs-create-vs-checkout deadlock** (V-1) and slow-DB boundary behaviour (V-2, H-3): a run with induced lock waits / `lock_timeout` asserting bounded latency and 409/503 rather than hangs.
12. **Two API instances behind an LB** running the full suite (M-3): with deliberately skewed clocks on the two instances.
13. **Invariants in CI**: `scripts/check-invariants.sql` is manual; smoke-checkout ends without asserting `check-invariants.sql` queries 1–6 (BOOKED ⇔ one live ticket, seat↔booking_id coupling). Wire it into `smoke:checkout`.
